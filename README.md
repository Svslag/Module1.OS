# Модуль 1 · Проект 3 «Разбор журналов веб-сервера»

**Автор:** Шавкиев Аслан (блоки A, B, C — все уровни).

## Запуск

```bash
sudo apt-get install -y python3 strace procps gawk   # если чего-то нет
bash run_all.sh
```

Нужны Python 3.11+, `strace`, `ps`, `awk`. Результаты печатаются и сохраняются текстом в `output/`. Журналы — `project3/logs/` (40 файлов × 15 000 строк).

## Блок A

- `A_basic/errors.sh` — строки и 5xx по файлам, итог, файл с максимумом (`access_17.log`, 149).
- `strace -c` на `access_17.log` (`output/A2_*`):

| | `wc -l` | Python |

| топ-3 | `read` 54, `mmap` 8, `close` 5 | `read` 134, `stat` 72, `rt_sigaction` 66 |

## Блок B

`B_main/logsplit.py -n N` — N процессов через `os.fork`, результат родителю через `os.pipe`, родитель читает до EOF и делает `waitpid` каждому ребёнку.

- Доля 5xx по путям: `/api/payment` 0,75%, остальные 0,40–0,47%. По файлам выделяются `access_17.log` (0,99%) и `access_29.log` (0,88%).
- Сбой: `/api/payment` в `access_17.log` — 97 из 587 запросов (16,5%).
- Время (2 ядра): N=1 — 0,284 с, N=2 — 0,163 с (1,75×), N=4 — 0,144 с (1,98×).
- После работы `ps`: потомков 0, зомби 0.

## Блок C

- **Три способа вернуть результат** (`C_advanced/returns.py`, `compare_modes.sh`): `pipe` 0,208 с, `shared_memory` 0,224 с, временные файлы 0,218 с. Разница в пределах шума, так как результат мал, а основное время уходит на чтение файлов. Различаются набор вызовов (`pipe2/write`; `ftruncate/mmap/unlink` для `/dev/shm`; `mkdir/rename/unlinkat/rmdir`) и надёжность уборки.
- **Ctrl+C** (`demo_ctrlc.sh`, `output/C2_ctrlc.txt`): дети сбрасывают SIGINT в `SIG_DFL` и умирают сразу, родитель в `finally` добивает оставшихся, собирает `waitpid`, делает `shm.unlink()` и удаляет временную папку. Результат для всех способов: процессов 0, зомби 0, сегментов в `/dev/shm` 0.
- **Время сбоя** (`find_failure.py`): 5xx каждого пути склеиваются в кластеры с разрывом ≤5 мин, самый большой — сбой: 10:47:05 → 11:22:36.

## Выводы

1. Жалобы связаны со сбоем оплаты 21.10 с 10:47 до 11:22. Остальные пути работали штатно.
2. Параллельный разбор через `fork + pipe` ускоряет работу ≈ в 2 раза на 2 ядрах; N стоит брать по числу ядер.
3. Способ возврата результата на скорость почти не влияет; `pipe` проще и безопаснее всего, `shared_memory` требует явного `unlink`.
4. Дополнительно: слабый всплеск 5xx на всех путях 22.10 10:26–10:40 (`access_29.log`, 4,2%).
